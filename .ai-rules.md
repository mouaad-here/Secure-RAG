# .ai-rules.md — Antigravity Agent Rules
# Project: Secure Local RAG MVP

> These rules govern every Antigravity session on this codebase.
> They are not suggestions. Deviate only with explicit team approval,
> documented in `.ai-context/PROGRESS_TRACKER.md`.

---

## 1. MANDATORY BOOT SEQUENCE

Before planning, writing, or modifying ANY code, Antigravity MUST read
all six context files in this exact order:

```
1. .ai-context/PROJECT_OVERVIEW.md
2. .ai-context/ARCHITECTURE.md
3. .ai-context/CODE_STANDARDS.md
4. .ai-context/AI_WORKFLOW_RULES.md
5. .ai-context/UI_CONTEXT.md
6. .ai-context/PROGRESS_TRACKER.md
```

After reading, state: current phase · current unit · last completed unit.
Wait for user to confirm before proceeding.

---

## 2. BUILD UNIT SKILL — TWO MODES

Every unit execution follows one of two modes. The spec file declares
which mode applies (`Mode: BACKEND` or `Mode: UI`). Never mix steps
from both modes in a single execution.

---

### MODE A — BACKEND UNIT
*Use for: Python modules, security logic, storage, ingestion, retrieval,
generation, config, Docker, CI. Any unit with no visual output.*

```
STEP 1  BOOT       Read all 6 context files → state phase + unit
STEP 2  SPEC       Read .ai-context/specs/{unit-name}.md
STEP 3  PROGRESS   Mark unit IN PROGRESS in PROGRESS_TRACKER.md
STEP 4  PLAN       List every file to create/modify + exact changes
                   List new deps (if any) + security implications
                   ── PAUSE: wait for human approval ──
STEP 5  EXECUTE    Write code file by file per the approved plan
STEP 6  VERIFY
                   docker compose exec api pytest {test_file} -v
                   docker compose exec api mypy {module_path}
                   curl commands from spec Verification section
                   Show passing output as the Verification Artifact
STEP 7  CLOSE      Mark COMPLETE · log decisions · state next unit
```

**Cost: LOW** — no browser, no screenshots, terminal output only.

---

### MODE B — UI UNIT
*Use for: Dashboard panels, HTML/JS/CSS, any visual component,
API shape changes that the dashboard consumes.*

```
STEP 1  BOOT       Read all 6 context files → state phase + unit
STEP 2  SPEC       Read .ai-context/specs/{unit-name}.md
STEP 3  PROGRESS   Mark unit IN PROGRESS in PROGRESS_TRACKER.md
STEP 4  PLAN       List every file to create/modify + exact changes
                   Include: component tree · API calls · state shape
                   ── PAUSE: wait for human approval ──
STEP 5  EXECUTE    Write code file by file per the approved plan
STEP 6  VERIFY
                   Run: pytest relevant unit tests
                   Launch: docker compose up (or vite dev server)
                   Open: integrated browser → http://localhost:5173
                     or  http://localhost:8000/dashboard
                   Capture: screenshot as Verification Artifact
                   Check: browser console for API errors
STEP 7  CLOSE      Mark COMPLETE · produce Walkthrough Artifact
                   State next unit clearly
```

**Cost: MEDIUM** — browser + screenshot only for actual UI panels.
Never open the browser during a MODE A unit. This is the main
cost saving vs running the full 11-step skill on every unit.

---

### MODE DECISION TREE

```
Does the unit produce visual output the user interacts with?
  YES → MODE B
  NO  → Does it change an API response shape AND the dashboard exists?
          YES → MODE B
          NO  → MODE A
```

## 3. SPEC FILES

Every unit has a spec at: `.ai-context/specs/{phase}-{id}_{slug}.md`

```
Phase 0 specs:   .ai-context/specs/0.1_repo-init.md
                 .ai-context/specs/0.6_config.md  ...
Phase 3 specs:   .ai-context/specs/3.2_injection-detector.md ...
Dashboard specs: .ai-context/specs/dash-1_upload-panel.md ...
```

**If a spec file does not exist:**
1. Do NOT proceed with execution.
2. Generate the spec using `_SPEC_TEMPLATE.md` as the base.
3. Present to user for approval.
4. Save it, then begin at STEP 3 of the appropriate mode.

## 4. SECURITY IS NON-NEGOTIABLE

| Situation | Required Action |
|-----------|----------------|
| Input from any external source | Validate with Pydantic before use |
| Any string going into a prompt | Pass through `scanner.py` logic |
| Any LLM response | Pass through `output_firewall.py` before return |
| URL or domain in any data | Check against `URL_ALLOWLIST` env var |
| Trust score computation | Default to quarantine, never to trusted |
| Logging sensitive data | Metadata only, never raw document content |
| New environment variable | Add to `.env.example` with a comment |

**[CHECKPOINT] required before touching:** trust score logic ·
collection routing · output firewall decisions · prompt template ·
regex patterns · audit log schema · TRUST_THRESHOLD loading.

Format: *"[CHECKPOINT] I am about to [action]. This affects
[security property]. My approach is [explanation]. Shall I proceed?"*

---

## 5. LAYER BOUNDARY RULES

```
api/         → may import: ingestion/ retrieval/ generation/ security/ config
ingestion/   → may import: security/ storage/ config
retrieval/   → may import: storage/ security/ config
generation/  → may import: retrieval/ (read-only) security/ config
security/    → NO internal app imports
storage/     → NO internal app imports
config.py    → NO internal app imports
dashboard/   → NO direct app/ imports — HTTP only (calls localhost:8000)
```

Boundary violation = stop + raise to user before continuing.

---

## 6. TRUST BOUNDARY RULES

- `chroma_trusted` and `chroma_quarantine` are never merged or co-queried.
- Collection assignment is set at ingestion and never changed at runtime.
- Retriever queries ONLY `chroma_trusted` in normal operation.
- `TRUST_THRESHOLD` always comes from `settings`, never hardcoded.

---

## 7. CODING CONSTRAINTS

| Rule | Value |
|------|-------|
| Language (backend) | Python 3.11 |
| Language (dashboard) | Vanilla JS + Vite or React |
| Max function length | 40 lines |
| Max file length | 200 lines |
| Type hints | Required on all signatures |
| Docstrings | Required on all public functions/classes |
| Hardcoded config values | Never — use `settings.*` |
| `eval()` / `exec()` | Never |
| `subprocess.shell=True` | Never |
| Raw content at INFO log | Never |
| Security regex inline | Never — always in `security/patterns.py` |

---

## 8. GIT RULES

- Commit on the branch matching the current phase only.
- Format: `type(scope): description`
  Types: `feat` `fix` `docs` `test` `refactor` `chore` `security` `ui`
- Never commit: `.env` · `data/` · `*.db` · `*.sqlite` · `redteam_docs/`
- Every commit must leave `pytest tests/unit/` green.

---

## 9. WHAT ANTIGRAVITY MUST NEVER DO

- Guess at a security decision
- Add a dependency without proposing it first
- Modify `ARCHITECTURE.md` or `CODE_STANDARDS.md` unilaterally
- Skip tests for any security module
- Execute two units without explicit user request
- Use any cloud LLM API (Ollama only — hard constraint)
- Open the browser during a MODE A unit
- Start a unit without first reading its spec file

## 10. EXTENSION READINESS

| Future Extension | How to Prepare Now |
|------------------|--------------------|
| Swap ChromaDB | `BaseVectorStore` interface in `storage/` |
| Swap Ollama | `BaseLLMClient` interface in `ollama_client.py` |
| More file types | Loader registry dict in `loader.py` |
| Auth / multi-tenant | `owner_id` nullable on all records |
| Full web app | Dashboard is already a standalone app calling the API |
| Plugin scanners | `List[ScannerPlugin]` in `scanner.py` |
| External metrics | JSONL metrics, not print statements |
